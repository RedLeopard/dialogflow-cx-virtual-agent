SOLUTION ARCHITECTURE / AT A GLANCE

One conversation.
A connected cloud system.

Twilio handles the call, Dialogflow CX manages the conversation, and authenticated Cloud Run fulfillment coordinates AI answers and customer actions.

CREDENTIAL STORAGE

Google Secret Manager

The documented deployment stores the Twilio Auth Token in Secret Manager and supplies it to Cloud Run through a secret-backed environment variable. The source reads the value at runtime.

IDENTITY & ACCESS

Service identity

The setup grants the backend identity access to the Twilio secret. Dialogflow’s exported webhook configuration uses service-agent ID tokens for Cloud Run invocation.

TELEPHONY BOUNDARY

Protected call screening

The transfer Function uses Twilio’s Protected visibility. Unsigned requests are checked by the platform before the call-screening handler runs.

04 / THE PROJECT ARCHITECTURE

Conversation in front.
Cloud engineering behind it.

Twilio handles the phone channel and live transfer. Dialogflow manages state, and an authenticated Cloud Run webhook coordinates Gemini and customer actions.

  1. 01 / PHONE CHANNEL

    Twilio Studio

    Connects incoming calls to Maya and routes live handoffs to the owner.

  2. 02 / CONVERSATION

    Dialogflow CX

    Manages intents, contact intake, conversation pages, and outcome routing.

  3. 03 / FULFILLMENT

    Cloud Run + FastAPI

    Validates webhook requests and coordinates booking texts and notifications.

  4. 04 / UNDERSTANDING

    Vertex AI + Gemini

    Uses conversation context for service answers, corrections, and project summaries.

Authenticated service boundaries

Dialogflow invokes the private Cloud Run backend using service-agent ID tokens. A dedicated runtime service account accesses Vertex AI, and the Twilio Auth Token is referenced from Google Secret Manager as a runtime secret. Current IAM grants, secret versions, and caller-data retention remain operational verification items.

Latency and operational choices

A minimum Cloud Run instance is kept warm to reduce startup pauses. Conversational model requests use minimal thinking, an eight-second limit, and no automatic retries. This controls one part of the call’s latency.
